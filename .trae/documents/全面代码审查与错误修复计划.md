# PDF邮件合并工具 - 全面代码审查与错误修复计划

## 项目概述
对 PDF 邮件合并工具（`src/` 目录下的 6 个核心模块）进行全面审查，识别并修复所有可能导致运行出错的问题。

---

## 发现的问题清单

### 🔴 严重问题（Critical）- 必然导致运行崩溃

#### 问题1：`requirements.txt` 缺少 `PyMuPDF` 依赖
- **文件**: [requirements.txt](file:///c:/Users/marike/Desktop/pdf/requirements.txt)、[pdf_processor.py:8](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L8)
- **根本原因**: `pdf_processor.py` 在模块顶层 `import fitz`（PyMuPDF），但 `requirements.txt` 中未列出 `PyMuPDF`
- **影响**: 任何 `from src import ...` 或 `from src.cli import ...` 都会触发 `ModuleNotFoundError: No module named 'fitz'`，导致整个包无法加载
- **修复方案**: 在 `requirements.txt` 中添加 `PyMuPDF>=1.23.0`

#### 问题2：`pdf_processor.py` 的 `fill_form_pdf` 只填充最后一页的表单域
- **文件**: [pdf_processor.py:88-91](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L88-L91)
- **根本原因**: `writer.update_page_form_field_values(writer.pages[-1], data)` 仅对最后一页调用表单填充
- **影响**: 多页 PDF 中分布在不同页面的表单字段无法被正确填充，只填充最后一页的字段
- **修复方案**: 遍历所有页面，对每一页都调用 `update_page_form_field_values`

#### 问题3：`interactive_cli.py` 的 `main()` 函数未将命令行参数传递给 `run()`
- **文件**: [interactive_cli.py:721-729](file:///c:/Users/marike/Desktop/pdf/src/interactive_cli.py#L721-L729)
- **根本原因**: `else` 分支调用 `cli.run()`（无参数），`run()` 方法中 `args` 默认为 `None`，导致始终进入交互模式
- **影响**: 用户执行 `python -m src.interactive_cli -t template.pdf -d data.csv` 时，命令行参数被忽略，强制进入交互模式
- **修复方案**: 将 `cli.run()` 改为 `cli.run(sys.argv[1:])`

### 🟠 高风险问题（High）- 特定条件下必然出错

#### 问题4：`interactive_cli.py` 的 `clean_path_quotes` 引号判断逻辑错误
- **文件**: [interactive_cli.py:164](file:///c:/Users/marike/Desktop/pdf/src/interactive_cli.py#L164)
- **根本原因**: `temp.count('"') == temp.count('"')` 比较的是同一个字符（`"`），条件永远为 True
- **影响**: 无法正确检测路径中不匹配的引号，当路径包含内部引号时可能导致路径错误
- **修复方案**: 移除此无意义判断，直接移除首尾引号即可

#### 问题5：`interactive_cli.py` 的 `run_interactive` 使用递归实现重试，可能导致栈溢出
- **文件**: [interactive_cli.py:691](file:///c:/Users/marike/Desktop/pdf/src/interactive_cli.py#L691)
- **根本原因**: 用户反复选择"重新开始"时，`self.run_interactive()` 被递归调用
- **影响**: 多次重试后触发 `RecursionError: maximum recursion depth exceeded`
- **修复方案**: 将递归改为 `while True` 循环

#### 问题6：`pdf_processor.py` 的 `replace_text` 不支持中文文本替换
- **文件**: [pdf_processor.py:186-191](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L186-L191)
- **根本原因**: `page.insert_text()` 使用 PyMuPDF 默认字体（helv/Helvetica），该字体不支持 CJK 字符。当替换值包含中文时，文本将显示为空白或乱码
- **影响**: 作为面向中文用户的工具，任何包含中文的占位符替换都会失败
- **修复方案**: 使用 `page.insert_text()` 的 `fontname="china-ss"` 参数指定中文字体

### 🟡 中风险问题（Medium）- 不良实践，可能导致意外行为

#### 问题7：`pdf_processor.py` 的 `fill_form_pdf` 异常重包装
- **文件**: [pdf_processor.py:92-103](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L92-L103)
- **根本原因**: 第93行抛出的 `PDFProcessError("PDF has no form fields to fill")` 被第102行的 `except Exception` 捕获并重新包装
- **影响**: 错误信息被包装成 `"Error filling PDF form: PDF has no form fields to fill"`，降低了错误可读性
- **修复方案**: 在 `except` 块中先判断异常类型，避免重复包装 `PDFProcessError`

#### 问题8：多处使用裸 `except:` 捕获所有异常
- **文件**:
  - [data_loader.py:89](file:///c:/Users/marike/Desktop/pdf/src/data_loader.py#L89)
  - [template_engine.py:115](file:///c:/Users/marike/Desktop/pdf/src/template_engine.py#L115)
  - [template_engine.py:195](file:///c:/Users/marike/Desktop/pdf/src/template_engine.py#L195)
  - [template_engine.py:205](file:///c:/Users/marike/Desktop/pdf/src/template_engine.py#L205)
  - [pdf_processor.py:183](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L183)
  - [utils.py:354](file:///c:/Users/marike/Desktop/pdf/src/utils.py#L354)
- **根本原因**: `except:` 不指定异常类型，会捕获 `SystemExit`、`KeyboardInterrupt` 等不应被吞掉的异常
- **影响**: 程序无法通过 Ctrl+C 中断，系统退出信号被静默忽略
- **修复方案**: 全部改为 `except Exception:`

#### 问题9：`pdf_processor.py` 的 `get_pdf_info` 重复调用 `get_form_text_fields()`
- **文件**: [pdf_processor.py:229](file:///c:/Users/marike/Desktop/pdf/src/pdf_processor.py#L229)
- **根本原因**: 同一行中 `get_form_text_fields()` 被调用了两次
- **影响**: 性能浪费（读取两次表单数据），虽然不会崩溃但属于不良实践
- **修复方案**: 使用变量缓存结果
